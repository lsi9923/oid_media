# oid_media — 민담 스튜디오

**바로 쓰기 → https://lsi9923.github.io/oid_media/**

민담 유튜브 채널 제작 워크플로우를 **27단계로 나눠 하나씩 따라가는** 웹 작업 도구입니다.

설치 없이 위 주소로 바로 쓸 수 있습니다. 백엔드가 없고 입력한 내용은 브라우저에만 저장되므로 계정도 필요 없습니다.

강의 [100% 수익창출 성공한 유튜브 강의, 유료강의 듣지마세요. (26년 7월 최신판)](https://www.youtube.com/watch?v=IFxreFxzvKQ) (돈버니 채널 · 행크 출연)의 제작 순서를 그대로 옮겼습니다. 각 단계에 원본 영상의 해당 지점 링크가 붙어 있어, 막히면 바로 그 장면으로 이동할 수 있습니다.

## 먼저 읽어야 할 것 — 수익화 정책

**이 방식은 YouTube 수익화 정책 두 범주에 걸릴 소지가 있습니다.** 앱의 첫 단계가 정책 확인인 이유입니다.

YouTube는 2025년 7월 `repetitious content` 정책을 `inauthentic content`로 개칭하고, 2026년 7월 수익화 불가 3개 범주를 명시했습니다.

| 범주 | 원문 |
|---|---|
| 일반적이거나 반복적인 콘텐츠 | Generic or Repetitive Content |
| 만족스럽지 않거나 불쾌한 콘텐츠 | Unsatisfying or Off-putting Content |
| 민감한 주제의 AI 페르소나 | AI Personas Related to Sensitive Topics |

가장 큰 위험은 첫 범주의 이 문구입니다.

> Videos where characters are put in the same situation over and over again with the same outcome (i.e., **using a highly similar storyline template across multiple videos**)

이 방식의 대본 프롬프트는 9단계 골격과 반전 여섯 개를 고정 틀로 씁니다. 주인공만 바꿔 반복하면 위 문구에 정확히 해당합니다. 그래서 프롬프트에 **골격 변주 규칙**을 넣었습니다. 시작점 4가지, 결말 유형 6가지, 조력자 유형 5가지를 돌려 쓰고, 반전 개수도 고정하지 않습니다.

### 강의 설명과 공식 정책이 어긋나는 지점

앱에서 3건을 짚어뒀습니다. 가장 중요한 것은 이것입니다.

| | |

## 수익 기대치를 조정하세요

강의의 수익 사례(조회수 6만에 80만원)는 특정 채널의 결과입니다. 공개 자료로 확인되는 일반적인 수준은 다릅니다.

| 항목 | 수치 | 신뢰도 |
|---|---|---|
| 전 니치 RPM 중위값 | 약 $2.30 / 1,000회 | 상업 분석 (AIR, 300채널) |
| Entertainment 니치 RPM | 약 $2.43 / 1,000회 | 상업 분석 |
| 한국 대 미국 CPM | 약 1 대 4 | 상업 분석 |
| 중간광고 활성 조건 | 영상 8분 이상 | **공식** |
| 수익 배분 | 제작자 55% / YouTube 45% | **공식** |
| 2026년 롱폼 영상당 광고 수익 | 전년 대비 약 55% 하락 | 상업 분석 (Metricool) |

한국 시청자 기반 채널의 CPM은 미국 대비 약 4분의 1입니다. 앱에 각 수치의 출처와 신뢰도(공식/상업 분석/추정)를 함께 표시했습니다.

**업로드를 많이 하는 것 자체는 노출을 늘리지 않습니다.** YouTube 추천 시스템 책임자 Todd Beaupré는 수백만 채널 분석 결과 업로드 간격과 조회수 사이에 사실상 상관관계가 없다고 공개적으로 밝혔습니다. 많이 올리면 정책 리스크만 커집니다.

## 이게 무슨 도구인가

유튜브에 올릴 1~2시간 분량의 한국 민담 오디오 콘텐츠를, AI 도구를 조합해 만드는 과정을 관리합니다.

제작 흐름은 이렇게 흘러갑니다.

```
Claude (대본 46,000자)  ─┬─→ Flow (본문 이미지 40장)  ─┐
                         ├─→ Grok (인트로 영상 4컷)   ─┼─→ Vrew (TTS + 조합) → YouTube
                         └─→ Flow + 미리캔버스 (썸네일) ─┘
```

이 앱은 그 흐름에서 두 가지를 담당합니다.

1. **프롬프트 제공** — Claude에 넣을 지침 9종
2. **반복 작업 대행** — 대본 분할, 장면 파싱, 태그 검증, 진행 추적

영상을 실제로 만드는 것은 Claude·Flow·Grok·Vrew이고, 이 앱은 그 사이를 잇습니다.

## 프롬프트 9개가 들어 있습니다

앱 안에서 복사하거나 `.txt`로 내려받아 지정된 위치에 넣으면 됩니다. 파일명의 번호가 설치 순서입니다.

| 파일 | 위치 | 하는 일 |
|---|---|---|
| 01_민담대본_MAIN | 민담 대본 → **지침 칸** | 8관문. 주제 추천 → 인트로 → 인물 → 줄거리 → 46,000자 대본 → 썸네일 브리프 |
| 02_모티프뱅크 | 민담 대본 → **파일 업로드** | 한국 구전 민담 서사 모티프 42개. 4갈래 조합 재료 |
| 03_이름규칙 | 민담 대본 → **파일 업로드** | TTS 오독 회피. 발음 위험 6종 + 금지 목록 + 권장 이름 200개 |
| 04_스토리팩트틀 | 민담 대본 → **파일 업로드** | 9챕터를 쓸 때 인물·시간·설정이 어긋나지 않게 하는 대조표 |
| 05_민담이미지_MAIN | 민담 이미지 → 지침 칸 | 화풍 추출 → 인물 5명 고정 → 40장면(H8/M16/L16). 영어 출력 |
| 06_민담인트로_MAIN | 민담 인트로 → 지침 칸 | Grok용 Scene 1~4. 대사·감정지시·이미지프롬프트·영상변환지시 |
| 07_민담썸네일_MAIN | 민담 썸네일 → 지침 칸 | 카피 후보 8개 → 배경 프롬프트 → 미리캔버스 수치 지시 |
| 08_Vrew에이전트_명령어 | Vrew 에이전트 | 이미지 40장 자동 배치 + 화면 효과 |
| 09_Vrew_주의점 | 참고 문서 | TTS 분할, 음성 중복, 자주 나는 문제와 해결 |

**지침 칸 4개 / 파일 업로드 3개를 반드시 구분하세요.** 섞으면 작동하지 않습니다.

프롬프트 총 약 3만 자입니다. 강의 명세를 바탕으로 새로 작성한 것이며, 강의 제작자의 원본 자료가 아닙니다. 원본을 받으셨다면 실적으로 검증된 자료이므로 그쪽을 쓰는 편이 낫습니다.

## 반복 작업을 대신하는 부분

| 기능 | 하는 일 |
|---|---|
| **대본 TTS 검사** | 프롬프트가 금지한 표기(한자·영문·괄호·아라비아 숫자·이모지)가 남았는지 46,000자를 훑어 줄·열 위치로 보고합니다. 숫자는 **단위에 맞는 한글 읽기**를 제안합니다 — 5시→다섯 시(고유어), 3년→삼 년(한자어), 100명→백 명. 자동 교정 버튼도 있습니다. |
| **템플릿 반복 방지 이력** | 정책 최대 리스크를 실제로 관리합니다. 영상별 구조(시작점·결말·조력자·주인공·모티프)를 채널별로 기록하고, 다음 영상이 겹치면 즉시 경고합니다. 겹치지 않는 조합을 추천하고 다양성 점수를 냅니다. |
| **작업 내용 백업** | 모든 데이터가 브라우저에만 있으므로 파일로 내보냅니다. 전체 백업(.json)과 대본만(.txt) 두 가지. 가져올 때 타입을 검증하고 덮어쓰기 전에 확인합니다. |
| 대본 분할기 | Vrew는 클립당 1만자만 받습니다. 46,000자 대본을 **문장 경계에서** 잘라 조각별 복사 버튼을 제공합니다. 문장 중간에서 끊기면 TTS 억양이 어긋납니다. |
| 장면 큐 | 40장면 프롬프트를 자동 분리하고 강도(H/M/L) 분배를 집계합니다. **@인물 태그 누락**을 잡아냅니다. 태그가 빠지면 그 장면만 얼굴이 달라집니다. |
| 간격 타이머 | 이미지 생성 2분 간격을 카운트다운합니다. 남은 장수 기준 예상 완료 시간(40장 = 1시간 20분)을 보여줍니다. |
| 인물 보관함 | Flow에서 고정한 인물 5명의 이름·프롬프트를 보관하고 `@태그`를 복사합니다. |
| 재료 보관함 | 대본과 썸네일 브리프를 저장합니다. 3·4단계에서 다시 필요한 재료입니다. |
| 카피 선택기 | 썸네일 카피 후보를 나열하고 하나를 고르게 합니다. 글자수를 함께 표시합니다. |
| 진행률 추적 | 단계별 체크리스트와 전체 진행률. 새로고침해도 유지됩니다. |
| 비용 계산 | 도구별 월 비용과 월 제작 편수 기준 영상 1편당 원가. |

## 8개 페이즈 · 28단계

| 페이즈 | 단계 | 목적 |
|---|---|---|
| **! 정책 · 리스크** | **1** | **시작 전 수익화 정책 확인. 걸릴 지점 6개와 대응책 24개** |
| 0 세팅 | 3 | 도구 결제 + 프롬프트 확보 + Claude 프로젝트 4개 |
| 1 대본 | 6 | 주제 선택 → 46,000자 대본 + 썸네일 브리프 |
| 2 이미지 | 5 | 인물 5명 고정 → 장면 40장 생성 |
| 3 인트로 | 3 | Grok으로 도입 4컷 |
| 4 썸네일 | 3 | 카피 선택 → 이미지 → 글자 입히기 |
| 5 Vrew 조합 | 4 | TTS + 이미지 + 인트로 합치기 |
| 6 업로드·운영 | 3 | AI 제작 표시 → 업로드 → 다채널 |

★ 표시가 붙은 4개 단계(정책 확인, 인트로 검수, 인트로 다듬기, 썸네일 카피 선택)는 **사람이 판단해야 하는 지점**입니다. 강의의 핵심 주장이 여기 있습니다 — 만드는 법과 돈 버는 법은 다르고, 시청자가 보는 건 썸네일과 인트로뿐입니다. 그리고 정책이 요구하는 "제작자의 관점"도 이 판단에서 나옵니다.

## 프롬프트를 어떻게 검증했나

프롬프트는 "잘 될 것 같다"로 끝내면 안 되므로 실제로 돌려 확인했습니다.

**방법.** 독립 서브에이전트에게 프롬프트 파일만 읽게 하고 실행시켰습니다. 에이전트는 제작 의도를 모르고 프롬프트 텍스트만 봤습니다. 나온 산출물을 앱의 실제 파서와 프롬프트가 선언한 규칙으로 기계 검사했습니다.

**1차 실행에서 드러난 결함 4개:**

| 결함 | 원인 | 수정 |
|---|---|---|
| 주제 제목이 25자 초과 | "스물다섯 자 안쪽"이 공백 포함 여부를 밝히지 않음. 자기 검증 단계 없음 | 공백 제외로 명시 + 출력 전 글자수 세기 단계 추가 + 길이 초과 나쁜 예 제시 |
| 장면 등급을 잘못 읽음 | **앱 파서 버그.** 본문의 `low angle`, `high saturation`을 등급으로 오인 | `detectIntensity`가 줄머리 대괄호만 읽도록 수정 |
| 안내문이 장면 태그를 오염 | 프롬프트가 지시한 안내문의 `@태그가`가 인물 태그로 잡힘 | 장면 종료선 도입 + `extractCharacterTags`로 일반어 제외 |
| 인트로 대사가 6초 초과 | "대사를 고치지 말라"와 "6초 제한"이 충돌. 우선순위 없음 | 컷 분할 절차 3단계 + 지시 충돌 시 우선순위 명시 |

두 번째 항목이 가장 중요합니다. 프롬프트가 아니라 **앱 코드의 버그**였고, 프롬프트 검증을 하지 않았다면 사용자가 장면 등급이 틀린 것을 눈치채기 어려웠을 것입니다.

**2차 실행.** 고친 프롬프트를 새 독립 에이전트로 다시 돌려 4개 결함이 모두 해소된 것을 확인했습니다. 1차 산출물 검사(`agent-output.test.ts`)는 결함 기록으로 남겼고, 2차 확인은 `retest.test.ts`에 있습니다.

**3차 — 가장 위험한 구간 검증.** 46,000자를 9챕터로 이어 쓰는 관문 7이 마지막까지 미검증이었습니다. 독립 에이전트에게 다섯 챕터(한 시간 분량)를 실제로 쓰게 하고 검사했습니다.

| 검사 | 결과 |
|---|---|
| 분량 | 22,924자 (목표 23,000자의 99.7%) |
| 챕터별 균형 | 최대/최소 비 1.5배 이내 |
| 설정 유지 4건 | 모두 지켜짐 (문맹·다리·열쇠·거리) |
| TTS 금지 표기 | 본문에 0건 |
| 어휘 통일 | 곳간·큰마님 일관 유지 |
| 구조 변주 반영 | 지정한 폭로형 결말·조력자 없음 반영 |

에이전트가 보고한 가장 어려웠던 지점은 "해주는 글을 읽지 못한다"였습니다. 문서를 발견한 뒤 내용을 알아가는 과정을 흙바닥에 글자를 그려 다른 인물에게 읽게 하는 방식으로 우회했습니다. 제약이 이야기를 오히려 밀도 있게 만든 사례입니다.

**독립 감사.** 새로 만든 도구 3개를 별도 감사자에게 결함 위주로 검사시켰습니다. 치명적 결함 2건이 나왔습니다.

| 결함 | 내용 |
|---|---|
| **`시`를 한자어로 분류** | `5시` → "오 시"로 자동 교정. 올바른 한국어는 "다섯 시"(고유어). **자동 교정이 원본보다 더 틀린 대본을 만들고 있었습니다.** `대`·`장`도 같은 오류였습니다. |
| **`스무`를 단독형으로 제시** | "스무"는 관형사여서 단독으로 쓸 수 없습니다. 단독형은 "스물". 관형사형과 단독형을 분리했습니다. |

사소한 결함 3건(100 이상 고유어 단위 제안 불가, 백업 가져오기 타입 미검증, 정규식 위험)도 함께 고쳤습니다. 전부 회귀 테스트를 붙였습니다.

**검증 규모.** 테스트 293개. 브라우저 검증은 배포된 사이트를 대상으로 별도 실행합니다.

남는 한계: 서브에이전트가 실제 Claude 프로젝트 환경과 완전히 같지는 않습니다. 파일 업로드 방식, 46,000자를 9챕터로 이어 쓸 때의 사용량 한도, 모델 차이에서 오는 편차는 직접 써봐야 드러납니다. 관문 7의 챕터 연속 집필은 챕터 1만 테스트했습니다.

## 데이터가 사라지지 않게 하세요

이 앱은 백엔드가 없어 모든 내용이 브라우저 localStorage에만 저장됩니다. 대본 생성에 15~20분이 걸리므로, **다 만든 뒤에는 바로 내보내 두세요.**

- **전체 백업(.json)** — 진행 상황, 대본, 장면, 인물, 이력을 모두 담습니다. 다른 기기로 옮길 때 씁니다.
- **대본만(.txt)** — 대본 원문만 별도 보관용.

가져올 때는 값의 타입을 검사하고, 덮어쓰기 전에 무엇이 들어오는지 보여준 뒤 확인을 받습니다.

## 배포

`main`에 푸시하면 GitHub Actions가 타입체크 → 테스트 → 빌드를 거쳐 GitHub Pages로 배포합니다(`.github/workflows/deploy.yml`).

경로가 하위 디렉터리(`/oid_media/`)이므로 Vite `base`를 저장소 이름에 맞춰뒀습니다(`vite.config.ts`의 `REPO_BASE`).

**저장소 이름을 바꾸면 `REPO_BASE`도 함께 바꿔야 합니다.** 안 바꾸면 JS·CSS 경로가 404가 되어 흰 화면만 나옵니다.

다른 호스트(Netlify, Vercel 등)에 루트로 올릴 때는 base를 덮어쓰면 됩니다.

```bash
VITE_BASE=/ npx vite build
```

## 데이터 저장

입력한 모든 내용은 **브라우저 localStorage에만** 저장됩니다. 서버로 전송되지 않고, 백엔드도 없습니다. 외부 통신 코드가 아예 없는 순수 클라이언트 앱입니다.

브라우저 데이터를 지우면 함께 사라지므로, 대본처럼 중요한 산출물은 별도로 보관하세요. 우측 상단 초기화 버튼으로 전체를 지울 수 있습니다(두 번 눌러 확인).

## 유의사항

YouTube는 사람의 개입 없이 대량 생산된 콘텐츠(AI 슬롭)를 제재합니다. 강의에서도 **클릭 한 번으로 영상까지 나오는 완전 자동화는 채널 삭제 사유**라고 반복해서 강조합니다. 이 앱이 각 단계에 사람의 선택과 검수를 요구하도록 설계된 이유입니다.

AI 제작 고지는 영상 화면과 YouTube 업로드 설정 두 곳 모두에 표기하세요. 정책은 수시로 바뀌므로 업로드 전 최신 기준을 직접 확인하시기 바랍니다.

수익은 주제·시청층·시기에 따라 크게 달라집니다. 강의에 나온 수치(조회수 6만에 80만원 등)는 특정 사례이며 보장된 결과가 아닙니다.
